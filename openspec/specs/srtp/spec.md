# srtp Specification

## Purpose

DTLS로 정한 SRTP 마스터 키와 솔트로 세션 키를 유도하고, 서버가 보내는 RTP 패킷을 암호화하고 인증 태그를 붙여 SRTP 패킷으로 만든다. 브라우저는 이 보호를 거친 패킷만 미디어로 받아들인다.

## Requirements

### Requirement: 세션 키 유도
서버는 SRTP 프로파일 `SRTP_AES128_CM_SHA1_80`의 마스터 키(16바이트)와 마스터 솔트(14바이트)에서 RFC 3711의 AES-CM 키 유도 함수로 암호화 키(16바이트), 인증 키(20바이트), 세션 솔트(14바이트)를 만들어야 한다(SHALL). 키 유도 주기(key derivation rate)는 0으로, 세션 키는 보호를 시작할 때 한 번만 유도한다. 키 값은 로그에 남기지 않는다.

#### Scenario: RFC 3711 키 유도 벡터
- **WHEN** RFC 3711 부록 B.3의 마스터 키와 마스터 솔트로 세션 키를 유도한다
- **THEN** 암호화 키, 인증 키, 세션 솔트가 부록 B.3의 기대값과 같다

### Requirement: RTP 패킷 보호
서버는 RTP 패킷을 보낼 때 RTP 헤더(CSRC와 확장 포함)는 평문으로 두고 페이로드를 AES-128 Counter Mode로 암호화해야 한다(SHALL). IV는 세션 솔트, SSRC, 패킷 인덱스(ROC와 순번으로 만든 48비트 값)로 RFC 3711 규칙에 따라 만든다. 암호화한 패킷 뒤에 인증 태그를 붙인 결과가 SRTP 패킷이다.

#### Scenario: RFC 3711 키스트림 벡터
- **WHEN** RFC 3711 부록 B.2의 세션 키와 IV로 키스트림을 만든다
- **THEN** 키스트림의 앞부분이 부록 B.2의 기대값과 같다

#### Scenario: 헤더는 평문
- **WHEN** RTP 패킷 하나를 보호한다
- **THEN** 결과 패킷의 RTP 헤더 바이트는 원래 패킷과 같고, 페이로드는 원래와 다르며 길이가 같고, 끝에 10바이트가 붙는다

### Requirement: 인증 태그
서버는 암호화한 RTP 패킷 전체에 그 패킷의 ROC(32비트, 네트워크 바이트 순서)를 이어 붙인 데이터로 인증 키를 사용해 HMAC-SHA1을 계산하고, 결과의 앞 10바이트(80비트)를 패킷 끝에 붙여야 한다(SHALL). ROC는 계산에만 쓰고 패킷에는 넣지 않는다.

#### Scenario: 브라우저가 받아들이는 패킷
- **WHEN** 서버가 DTLS로 정한 키로 보호한 패킷을 Chrome에 보낸다
- **THEN** `chrome://webrtc-internals`의 inbound-rtp 통계에서 받은 패킷 수가 늘어나고, SRTP 복호화 실패로 버려진 패킷이 없다

#### Scenario: 같은 키로 복호화
- **WHEN** 테스트가 같은 마스터 키와 솔트로 보호된 패킷의 태그를 검증하고 페이로드를 복호화한다
- **THEN** 태그 검증이 통과하고 복호화한 패킷은 보호 전 RTP 패킷과 같다

### Requirement: 송신 ROC 관리
서버는 SSRC마다 ROC를 0에서 시작하고, 보낸 RTP 순번이 65535 다음 0으로 넘어갈 때 ROC를 1 올려야 한다(SHALL). 송신하는 쪽이므로 순번은 항상 1씩 증가한다고 보고, 순서 재정렬 추정은 하지 않는다.

#### Scenario: 순번 순환
- **WHEN** 순번 65535인 패킷 다음에 순번 0인 패킷을 보호한다
- **THEN** 두 번째 패킷은 ROC 1로 IV와 인증 태그를 계산하며, 같은 키로 ROC 1을 가정한 복호화가 통과한다

### Requirement: SRTCP 세션 키 유도
서버는 DTLS-SRTP로 정한 브라우저 쪽(DTLS client) 마스터 키와 솔트에서 RFC 3711의 AES-CM 키 유도 함수로 SRTCP 암호화 키(16바이트, 레이블 0x03), 인증 키(20바이트, 레이블 0x04), 세션 솔트(14바이트, 레이블 0x05)를 만들어야 한다(SHALL). 키 유도 주기는 0이다. 서버가 보내는 RTP용 키와는 마스터 키와 레이블이 모두 다르다. 키 값은 로그에 남기지 않는다.

#### Scenario: RTP 레이블과 다른 키
- **WHEN** 같은 마스터 키와 솔트로 SRTP 세션 키와 SRTCP 세션 키를 유도한다
- **THEN** SRTCP의 암호화 키, 인증 키, 세션 솔트는 각각 SRTP의 같은 종류 키와 다르고, 레이블 0x03~0x05로 계산한 AES-CM 키스트림과 같다

### Requirement: SRTCP 패킷 검증과 복호화
서버는 받은 SRTCP 패킷의 끝 10바이트를 인증 태그로, 그 앞 4바이트를 E 비트와 31비트 SRTCP 인덱스로 읽어야 한다(SHALL). 인증 키로 태그 앞의 모든 바이트(인덱스 포함)에 HMAC-SHA1을 계산해 앞 10바이트가 태그와 같아야 받아들인다. E 비트가 1이면 첫 8바이트 뒤부터 인덱스 앞까지를 AES-128 Counter Mode로 복호화한다. IV는 세션 솔트, 패킷의 SSRC, SRTCP 인덱스로 만든다. 결과는 인덱스와 태그를 뺀 RTCP 데이터다.

#### Scenario: 보호한 패킷 복원
- **WHEN** 테스트가 브라우저 역할로 같은 마스터 키를 써서 RTCP 복합 패킷을 E 비트 1로 보호하고, 서버가 그것을 검증·복호화한다
- **THEN** 결과는 보호 전 RTCP 복합 패킷과 같다

#### Scenario: 변조한 패킷
- **WHEN** 보호한 패킷의 암호화된 부분이나 인덱스의 한 비트를 바꾼다
- **THEN** 인증 실패로 거부된다

#### Scenario: 너무 짧은 패킷
- **WHEN** RTCP 헤더 8바이트, 인덱스 4바이트, 태그 10바이트의 합보다 짧은 패킷이 도착한다
- **THEN** 길이 부족으로 거부된다

#### Scenario: 브라우저가 보낸 패킷
- **WHEN** Chrome이 연결된 세션으로 RTCP를 보낸다
- **THEN** 서버는 인증 실패 없이 검증과 복호화에 성공한다

### Requirement: SRTCP 재생 방지
서버는 SSRC마다 인증을 통과한 가장 큰 SRTCP 인덱스와 그 아래 64개 인덱스의 수신 여부를 기억하고, 이미 받은 인덱스나 가장 큰 인덱스보다 64 이상 작은 인덱스의 패킷을 거부해야 한다(SHALL). 수신 기록은 인증과 복호화를 모두 통과한 패킷으로만 갱신한다. 한 세션에서 기억하는 SSRC는 최대 8개이며, 그보다 많은 새 SSRC의 패킷은 거부한다.

#### Scenario: 같은 패킷 두 번
- **WHEN** 인증을 통과한 SRTCP 패킷과 같은 패킷이 다시 도착한다
- **THEN** 두 번째 패킷은 재생으로 거부된다

#### Scenario: 순서가 바뀐 패킷
- **WHEN** 인덱스 10 패킷 뒤에 아직 받지 않은 인덱스 9 패킷이 도착한다
- **THEN** 두 패킷 모두 받아들여진다

#### Scenario: 창보다 오래된 패킷
- **WHEN** 인덱스 100 패킷을 받은 뒤 인덱스 30 패킷이 도착한다
- **THEN** 인덱스 30 패킷은 재생으로 거부된다

#### Scenario: 인증 실패는 기록하지 않음
- **WHEN** 인덱스 5이지만 태그가 틀린 패킷 뒤에 인덱스 5인 올바른 패킷이 도착한다
- **THEN** 뒤의 패킷은 받아들여진다
