# Proposal

## Why

다음 change(`add-recording-playback`)에서 서버는 녹화 파일(fMP4)의 조각을 HLS로 브라우저에 보낸다. 브라우저의 HLS 재생기(hls.js)는 녹화 파일 하나에서 조각 하나만큼의 바이트 범위를 `Range` 헤더로 요청하고, 재생하는 동안 이런 요청을 1초에 한 번 정도 계속 보낸다.

지금 HTTP 서버는 이 요청을 처리할 수 없다. 두 가지 이유가 있다.

- 서버는 `Range` 헤더를 읽지 않고 항상 파일 전체를 `200 OK`로 보낸다.
- 서버는 파일 경로 확인(`stat`)과 파일 읽기(`read`)를 이벤트 루프 스레드에서 한다. 같은 스레드가 RTSP 카메라의 RTP 수신과 WebRTC SRTP 송신도 맡고 있다. 읽을 데이터가 페이지 캐시에 없으면 `read`가 디스크를 기다리는 동안(HDD에서 수~수십 ms) 그 처리가 모두 멈춘다. 녹화 스레드의 `fdatasync`와 디스크 I/O 큐를 나눠 쓰면 더 오래 멈출 수 있다.

녹화 change는 "디스크에 닿는 일은 이벤트 루프 스레드에서 하지 않는다"는 원칙으로 녹화 스레드를 따로 두었다. 이 change는 HTTP 파일 응답에도 같은 원칙을 적용하고, `Range` 요청에 응답하는 기능을 더한다. 녹화본 재생의 기반이 되는 부분이라 녹화본 재생과 나눠서 먼저 한다.

## What Changes

- 다른 스레드가 이벤트 루프 스레드에서 실행할 작업을 넘기는 기능을 `core::EventLoop`에 추가한다.
  - 다른 스레드는 작업을 넘긴 뒤 바로 돌아가고, 이벤트 루프가 다음 반복에서 그 작업을 실행한다.
  - 이 change에서는 파일 읽기 스레드가 읽기 결과를 넘길 때 쓴다. 다음 change에서는 녹화 스레드가 색인 갱신을 알릴 때도 쓴다.
- HTTP 서버가 파일을 여는 일, 파일 정보를 읽는 일, 파일 내용을 읽는 일을 파일 읽기 스레드에서 한다.
  - 파일 읽기 스레드는 HTTP 서버가 만들고 소유한다. 녹화 스레드와는 따로 둔다.
  - 이벤트 루프 스레드는 요청 경로의 문자열 검사(`..`, 시작 문자 `/`)만 하고, 파일 읽기 스레드가 결과를 넘기면 응답을 보낸다.
  - 파일 읽기 스레드가 읽는 동안 이벤트 루프 스레드는 다른 연결과 카메라·WebRTC 처리를 계속한다.
- GET 엔드포인트 핸들러가 응답 본문 대신 "이 파일을 보내라"(파일 경로와 `Content-Type`)를 돌려줄 수 있게 한다. 서버는 정적 파일과 같은 방식으로 그 파일을 읽어 응답한다. 다음 change의 녹화 파일 경로 핸들러가 이 방식을 쓴다.
- 파일 응답에서 `Range` 요청을 처리한다.
  - 범위 하나(`bytes=a-b`, `bytes=a-`, `bytes=-n`)를 요청하면 그 범위만 `206 Partial Content`와 `Content-Range`로 보낸다.
  - 범위가 파일 크기를 벗어나면 `416 Range Not Satisfiable`로 응답한다.
  - 범위가 여러 개이거나 형식이 잘못되었거나 `If-Range`가 함께 오면 `Range`를 무시하고 파일 전체를 `200 OK`로 보낸다.
  - 파일 응답에는 `Accept-Ranges: bytes`를 넣는다.
- 경로 검사를 통과한 파일이 열 때 없으면(검사 뒤 삭제됨) `404 Not Found`로 응답한다. **BREAKING**: 이전에는 `500 Internal Server Error`로 응답했다. 읽기 권한이 없는 경우는 이전처럼 `500`이다.

범위 밖:

- keep-alive. 응답 하나를 보낸 뒤 연결을 닫는 정책은 그대로다.
- 응답 본문을 나눠 읽어 보내기(스트리밍). 파일 읽기 스레드는 응답할 바이트 범위 전체를 메모리로 읽는다.
- 녹화 파일을 제공하는 경로, `.mp4`·`.m3u8`의 `Content-Type`, HLS 재생 목록. 다음 change에서 한다.
- `ETag`, `Last-Modified`, 조건부 요청(`If-None-Match` 등), `HEAD` 메서드

## Capabilities

### New Capabilities

없음

### Modified Capabilities

- `http-server`: 파일 응답의 범위 요청(`206`, `416`, `Accept-Ranges`)을 추가하고, 파일 읽기 중에도 다른 연결 처리를 멈추지 않는다는 조건을 "연결 수명"에 더하며, 경로 확인 뒤 삭제된 파일의 응답을 `404`로 바꾼다.

## Impact

- 새 코드
  - `src/core/event_loop.h/.cpp`: 다른 스레드에서 작업을 넘기는 기능(eventfd와 잠금으로 보호한 작업 큐)
  - `src/http/`: `Range` 헤더 해석과 범위 계산, 파일 읽기 스레드와 작업 큐
  - 대응하는 `tests/core/`, `tests/http/` 단위 테스트와 `tests/integration/http_server_test.sh`의 `curl -r` 시나리오
- 바뀌는 코드
  - `src/http/http_server.h/.cpp`: 연결에 "파일 읽기 결과 대기" 단계를 더하고, 정적 파일 응답을 파일 읽기 스레드로 옮긴다. GET 핸들러 반환형에 파일 응답을 더한다.
  - `src/http/http_request.h/.cpp`: `Range`, `If-Range` 헤더 값을 보관한다.
  - `src/http/http_response.h/.cpp`: `206`, `416` 상태 코드
  - `src/http/static_files.h/.cpp`: 경로 확인을 문자열 검사만 하도록 바꾸고, 파일 열기·확인·읽기를 파일 읽기 스레드용 함수로 옮긴다.
- 의존성: 새 라이브러리는 없다. 스레드는 C++ 표준 라이브러리로 만든다.
- 호환성: 웹 페이지와 시그널링 동작은 바뀌지 않는다. 경로 확인 뒤 삭제된 파일의 응답 코드만 `500`에서 `404`로 바뀐다.
