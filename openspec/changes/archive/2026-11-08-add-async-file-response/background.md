# Background

## 읽는 순서

이 문서를 먼저 읽고 proposal → specs/http-server → design → tasks 순서로 읽는다.

이 change의 큰 흐름은 다음과 같다. 지금 HTTP 서버는 파일 응답을 만들 때 이벤트 루프 스레드에서 디스크를 읽는다. 이 change는 파일을 여는 일과 읽는 일을 별도 스레드(파일 읽기 스레드)로 옮기고, 그 스레드가 결과를 이벤트 루프 스레드에 넘기는 방법(`EventLoop::Post`)을 만든다. 그리고 파일의 일부 바이트만 요청하는 HTTP 범위 요청(`Range`)에 응답한다. 다음 change에서 녹화 파일의 조각을 HLS로 보낼 때 이 두 기능을 쓴다.

## 개념

### 이벤트 루프와 블로킹 호출

#### 이벤트 루프

- **정의:** 스레드 하나가 여러 fd(소켓, 타이머 등)의 이벤트를 한꺼번에 기다렸다가, 이벤트가 생긴 fd의 처리 함수를 차례로 호출하는 구조.
- **왜 필요한가:** 연결마다 스레드를 두지 않고도 많은 연결을 동시에 처리할 수 있다. 상태를 한 스레드만 바꾸므로 잠금이 필요 없다.
- **동작:** 이 프로젝트의 `core::EventLoop`는 Linux `epoll_wait`로 이벤트를 기다린다. 처리 함수 하나가 오래 걸리면, 그동안 다른 fd의 이벤트는 처리되지 않고 기다린다. 이 서버에서 같은 스레드가 HTTP 연결, RTSP 카메라의 RTP 수신, WebRTC SRTP 송신, 타이머를 모두 처리하므로, 처리 함수 하나가 10ms 걸리면 그 10ms 동안 영상 패킷 송수신도 멈춘다.
- **이 change에서:** design 결정 1, 2. "루프 스레드"라고 부른다.

#### 블로킹 호출

- **정의:** 결과가 준비될 때까지 호출한 스레드를 돌려보내지 않는 시스템 호출.
- **왜 문제인가:** 이벤트 루프 스레드에서 블로킹 호출을 하면 위에서 말한 대로 다른 모든 처리가 멈춘다.
- **동작:** 소켓은 `O_NONBLOCK`으로 열면 데이터가 없을 때 바로 `EAGAIN`을 돌려준다. 하지만 일반 파일의 `read`는 `O_NONBLOCK`과 관계없이 데이터를 디스크에서 가져올 때까지 기다린다. 그래서 파일 읽기는 이벤트 루프로 기다릴 수 없고, 다른 스레드에서 해야 한다.
- **이 change에서:** proposal "Why", design "Goals".

#### 페이지 캐시

- **정의:** 운영체제가 최근에 읽거나 쓴 파일 내용을 메모리에 남겨 두는 영역.
- **왜 필요한가:** 같은 데이터를 다시 읽을 때 디스크에 가지 않아도 된다.
- **동작:** `read`가 요청한 바이트가 페이지 캐시에 있으면 메모리 복사만 하고 µs 단위로 끝난다. 없으면 디스크에서 읽어야 해서 SSD에서 수십~수백 µs, HDD에서 수~수십 ms 걸린다. 다른 스레드가 같은 디스크에 많이 쓰고 있으면(예: 녹화 스레드의 `fdatasync`) 더 기다릴 수 있다. 방금 녹화한 조각은 대개 캐시에 있고, 오래된 조각은 캐시에서 밀려나 있을 수 있다.
- **이 change에서:** proposal "Why", design 결정 3의 "녹화 스레드와 따로 두는 이유".

### 스레드 사이의 전달

#### 잠금과 조건 변수

- **정의:** `std::mutex`는 한 번에 한 스레드만 공유 데이터를 바꾸게 하는 잠금이고, `std::condition_variable`은 다른 스레드가 알려 줄 때까지 잠을 자게 하는 도구다.
- **왜 필요한가:** 루프 스레드가 작업을 넣고 파일 읽기 스레드가 꺼내는 큐는 두 스레드가 함께 바꾸므로 잠금이 필요하다. 큐가 비었을 때 파일 읽기 스레드가 계속 확인하며 CPU를 쓰지 않도록 조건 변수로 잠든다.
- **동작:** 넣는 쪽은 잠금을 잡고 큐에 넣은 뒤 `notify_one()`을 부른다. 꺼내는 쪽은 잠금을 잡고 `wait(잠금, 조건)`으로 큐가 빌 동안 잠들었다가 깨어나면 하나를 꺼낸다. 녹화 스레드(`RecordingWriter`)가 이미 같은 방식을 쓴다.
- **이 change에서:** design 결정 3의 `FileReader` 큐, 결정 2의 루프 작업 목록.

#### eventfd

- **정의:** Linux 커널이 제공하는 64비트 카운터 하나를 fd로 다루는 객체.
- **왜 필요한가:** 파일 읽기 스레드는 조건 변수로 깨울 수 있지만, 루프 스레드는 `epoll_wait`에서 잠들어 있어 조건 변수로는 깨울 수 없다. eventfd를 epoll에 등록해 두면 다른 스레드가 eventfd에 쓰는 순간 `epoll_wait`가 반환된다.
- **동작:**
  - `write(fd, 1)`: 카운터에 1을 더한다. 카운터가 0보다 커지면 fd가 읽기 가능해진다.
  - `read(fd)`: 카운터 값을 돌려주고 0으로 되돌린다. 0이 되면 다시 읽기 불가능해진다.
  - 예: 다른 스레드가 1을 세 번 쓰면 카운터는 3이 되고, 루프가 한 번 `read`하면 3을 받고 0이 된다. 루프는 깨어난 횟수가 아니라 "깨어날 일이 있었다"만 알면 된다.
- **이 change에서:** design 결정 2의 `EventLoop::Post`.

#### `std::weak_ptr`로 객체 수명 확인하기

- **정의:** `std::shared_ptr`이 가리키는 객체를 소유하지 않고 가리키다가, 객체가 아직 살아 있는지 확인할 수 있는 포인터.
- **왜 필요한가:** 파일 읽기 스레드가 결과를 넘기는 루프 작업은 `HttpServer`의 주소를 써야 한다. 그런데 그 루프 작업이 실행되기 전에 `HttpServer`가 소멸할 수 있다. 소멸한 객체의 주소를 쓰면 해제된 메모리에 접근한다.
- **동작:** `HttpServer`가 `std::shared_ptr`을 하나 들고 있고, 루프 작업은 그 `weak_ptr`을 가진다. `HttpServer`가 소멸하면 `shared_ptr`도 사라지고, 루프 작업이 `weak_ptr.expired()`나 `lock()`으로 확인했을 때 이미 없다는 것을 알 수 있다.
- **이 change에서:** design 결정 5의 "서버 수명 확인".

### TCP 연결 종료

#### FIN과 RST

- **정의:** TCP 연결을 끝낼 때 커널이 상대에게 보내는 두 가지 신호. FIN은 "나는 더 보낼 데이터가 없다"는 정상 종료 신호이고, RST는 "이 연결을 즉시 버린다"는 강제 종료 신호다.
- **왜 필요한가:** 서버가 응답을 준비하는 동안 클라이언트가 연결을 닫을 수 있다. 예를 들어 사용자가 브라우저 탭을 닫거나, curl을 Ctrl+C로 멈추거나, 재생기가 요청을 취소한다. 이때 클라이언트의 커널이 보내는 신호에 따라 서버가 알 수 있는 내용이 달라진다.
- **동작:**
  - 클라이언트 프로그램이 소켓에 `close()`를 호출하거나 프로세스가 끝나 커널이 소켓을 닫으면, 커널은 보통 FIN을 보낸다.
  - 커널이 FIN 대신 RST를 보내는 경우는 두 가지다. 클라이언트가 아직 읽지 않은 수신 데이터를 남긴 채 소켓을 닫은 경우와, `SO_LINGER`를 0초로 설정하고 닫은 경우다.
  - HTTP 요청만 보내고 응답을 기다리던 클라이언트는 서버에서 받은 데이터가 없으므로 읽지 않은 수신 데이터도 없다. 그래서 이 클라이언트가 `close()`하면 RST가 아니라 FIN이 나간다.
- **이 change에서:** design 결정 5, Risks의 `kWaitingForFile` 항목.

#### 반쯤 닫힘(half-close)

- **정의:** TCP 연결의 두 방향 중 한 방향만 닫힌 상태.
- **왜 필요한가:** FIN을 받은 서버가 무엇을 알 수 있고 무엇을 알 수 없는지 설명하려면, FIN이 연결 전체가 아니라 한 방향만 닫는다는 점을 알아야 한다.
- **동작:**
  - TCP 연결은 클라이언트 → 서버 방향과 서버 → 클라이언트 방향으로 이루어지며, FIN은 FIN을 보낸 쪽의 방향 하나만 닫는다.
  - 클라이언트가 FIN을 보내면 클라이언트 → 서버 방향만 닫힌다. 서버의 커널은 서버 → 클라이언트 방향이 아직 열려 있다고 보며, 서버는 이 방향으로 응답을 보낼 수 있다.
  - 클라이언트는 보내는 방향만 닫고 응답을 계속 받을 수 있다. `shutdown(SHUT_WR)`이 이 동작이다. 예: `nc -N`은 표준 입력을 다 보내면 `shutdown(SHUT_WR)`을 부르고 응답을 읽는다.
  - 서버는 FIN만 보고 클라이언트가 `shutdown(SHUT_WR)`으로 보내는 방향만 닫고 응답을 기다리는지, `close()`로 소켓을 완전히 닫고 떠났는지 구별할 수 없다. 두 경우 모두 서버가 받는 신호는 같은 FIN이다.
- **이 change에서:** design 결정 5, Risks의 `kWaitingForFile` 항목.

#### 클라이언트의 종료 동작과 epoll 이벤트

- **정의:** 클라이언트가 소켓을 닫는 방법에 따라 서버 소켓에 생기는 epoll 이벤트.
- **왜 필요한가:** 파일 읽기 결과를 기다리는 연결에서, 서버가 클라이언트의 종료를 어떤 경우에 바로 알 수 있고 어떤 경우에 알 수 없는지 설명하려면 종료 동작별 이벤트를 알아야 한다.
- **동작:**

  | 클라이언트의 동작 | 클라이언트 커널이 보내는 신호 | 서버 소켓에 생기는 epoll 이벤트 |
  | --- | --- | --- |
  | `shutdown(SHUT_WR)` | FIN | `EPOLLIN`, `EPOLLRDHUP` |
  | 읽지 않은 수신 데이터 없이 `close()` | FIN | `EPOLLIN`, `EPOLLRDHUP` |
  | `SO_LINGER`를 0초로 두고 `close()` | RST | `EPOLLIN`, `EPOLLRDHUP`, `EPOLLHUP`, `EPOLLERR` |

  이 표는 Linux에서 루프백 연결로 세 동작을 실행하고 서버 소켓의 epoll 이벤트를 읽어 확인한 결과다.

  - `EPOLLIN`: 소켓을 읽을 수 있다. FIN을 받은 뒤에 읽으면 0바이트(EOF)를 돌려준다.
  - `EPOLLRDHUP`: 상대가 보내는 방향을 닫았다(FIN 또는 RST를 받았다).
  - `EPOLLHUP`: 연결의 두 방향이 모두 끝났다. FIN만 받은 상태에서는 서버 → 클라이언트 방향이 아직 열려 있으므로 생기지 않는다. RST를 받으면 두 방향이 모두 끝나므로 생긴다.
  - `EPOLLERR`: 소켓에 오류가 있다. RST를 받으면 연결 재설정 오류(`ECONNRESET`)가 생긴다.
- **감시 이벤트를 0으로 등록한 소켓:** epoll은 등록한 감시 이벤트만 전달하지만, `EPOLLHUP`과 `EPOLLERR`는 등록하지 않아도 항상 전달한다. 감시 이벤트를 0으로 등록한 소켓에서 FIN을 받으면 `EPOLLIN`과 `EPOLLRDHUP`만 생기므로 서버 프로그램에는 아무 이벤트도 전달되지 않는다. RST를 받으면 `EPOLLHUP`과 `EPOLLERR`가 전달된다. 위 표의 확인에서도 감시 이벤트를 0으로 등록한 소켓에는 RST 경우에만 이벤트가 전달되었다.
- **이 change에서:** design 결정 5는 파일 읽기 결과를 기다리는 연결(`kWaitingForFile`)의 감시 이벤트를 0으로 둔다. 그래서 서버는 다음처럼 동작한다.
  - 클라이언트가 RST를 보내면 `EPOLLHUP`·`EPOLLERR`를 받고 연결을 바로 닫는다. `http_endpoint_test`는 이 경우를 만들려고 `SO_LINGER`를 0초로 두고 닫는다.
  - 클라이언트가 FIN을 보내면 아무 이벤트도 받지 않고 결과가 도착할 때까지 연결을 유지한다. 결과가 도착하면 응답을 보내고 연결을 닫는다. 클라이언트가 `shutdown(SHUT_WR)`으로 응답을 기다리는 중이었다면 응답을 정상으로 받는다. 클라이언트가 `close()`로 떠났다면 서버는 받을 사람이 없는 파일을 끝까지 읽은 셈이 된다.
  - FIN을 알리는 `EPOLLRDHUP`을 감시해 바로 닫지 않는 이유: 위의 "반쯤 닫힘"에서 본 것처럼 FIN만으로는 응답을 기다리는 클라이언트와 떠난 클라이언트를 구별할 수 없다. FIN이 오자마자 닫으면 응답을 기다리던 클라이언트가 응답을 받지 못한다.

### 파일과 fd

#### fd 번호 재사용

- **정의:** 프로세스가 fd를 닫으면, 그 번호는 다음에 여는 소켓이나 파일에 다시 쓰일 수 있다.
- **왜 문제인가:** 연결 A(fd 7)가 파일 읽기 결과를 기다리는 동안 끊겨서 닫히고, 새 연결 B가 fd 7을 받으면, 나중에 도착한 A의 결과를 "fd 7"만 보고 B에 보내게 된다.
- **동작:** 연결마다 다시 쓰지 않는 번호(1, 2, 3, ...)를 따로 붙여 두고, fd와 번호가 모두 같을 때만 결과를 보낸다.
- **이 change에서:** design 결정 5의 "연결 식별".

#### 열린 파일의 삭제(`unlink`)

- **정의:** Linux에서 파일을 지우는 `unlink`는 디렉터리에서 이름만 지운다. 파일 내용은 그 파일을 연 fd가 모두 닫힐 때 해제된다.
- **왜 필요한가:** 다음 change에서 녹화 스레드의 보관 정책이 파일을 지우는 순간 파일 읽기 스레드가 같은 파일을 읽고 있을 수 있다. 잠금 없이도 이미 연 fd로는 끝까지 읽을 수 있다.
- **동작:** `open` 전에 지워졌으면 `open`이 `ENOENT`(파일 없음)로 실패하고, 서버는 `404`로 응답한다. `open` 뒤에 지워졌으면 그 요청의 응답은 정상으로 끝난다.
- **이 change에서:** design 결정 6, specs "파일 읽기 실패 응답".

#### FIFO와 `O_NONBLOCK` 열기

- **정의:** FIFO(이름 있는 파이프)는 파일 시스템에 이름이 있는 파이프다. 한쪽 프로세스가 쓴 바이트를 다른 쪽이 읽는다.
- **왜 문제인가:** FIFO를 읽기 전용으로 열면, 쓰는 쪽이 열 때까지 `open`이 반환하지 않는다. 웹 루트에 FIFO가 있으면 파일 읽기 스레드가 그 `open`에서 멈춘다.
- **동작:** `O_NONBLOCK`을 붙여 열면 FIFO도 바로 열린다. 그 뒤 `fstat`으로 일반 파일이 아님을 확인해 `404`로 응답한다. 일반 파일에는 `O_NONBLOCK`이 아무 영향이 없다.
- **열기 전에는 FIFO인지 알 수 없는 이유:** 루프 스레드는 요청 경로의 문자열만 검사하고 파일 시스템을 조회하지 않는다. 파일 읽기 스레드가 경로를 열기 전에는 그 경로가 일반 파일인지 FIFO인지 확인한 곳이 없다. 그래서 파일 읽기 스레드는 모든 경로를 `O_NONBLOCK`을 붙여 연다.
- **`stat`으로 먼저 확인하지 않는 이유:** `stat`으로 경로의 종류를 확인한 뒤 `open`하면, 두 호출 사이에 다른 프로세스가 그 경로의 파일을 지우고 같은 이름의 FIFO를 만들 수 있다. 그러면 `stat`은 일반 파일이라고 알려 주었지만 `open`은 FIFO를 열게 된다. 먼저 열고 그 fd에 `fstat`을 호출하면 실제로 연 대상의 종류를 확인하므로 이런 경우가 생기지 않는다.
- **이 change에서:** design 결정 6의 1·2단계.

### HTTP 범위 요청

#### `Range`와 `206 Partial Content`

- **정의:** 클라이언트가 파일의 일부 바이트만 달라고 요청하는 HTTP 기능.
- **왜 필요한가:** HLS 재생기는 녹화 파일 하나(60초, 약 15MB) 안에서 조각 하나(약 1초)만 필요하다. 파일 전체를 받으면 필요 없는 데이터를 수십 배 받게 된다. 녹화 파일 형식(fMP4)과 색인은 조각의 위치와 크기를 기록해 두었으므로, 재생 목록이 `EXT-X-BYTERANGE`로 그 범위를 알려 주면 재생기가 `Range`로 요청한다.
- **동작:** 위치는 0부터 세고 끝 위치를 포함한다. 크기가 100바이트인 파일에서:

  | 요청 헤더 | 뜻 | 응답할 바이트 | `Content-Range` |
  | --- | --- | --- | --- |
  | `Range: bytes=0-9` | 0번부터 9번까지 | 0~9 (10바이트) | `bytes 0-9/100` |
  | `Range: bytes=90-` | 90번부터 끝까지 | 90~99 (10바이트) | `bytes 90-99/100` |
  | `Range: bytes=95-200` | 끝 위치가 파일 밖이면 파일 끝까지 | 95~99 (5바이트) | `bytes 95-99/100` |
  | `Range: bytes=-20` | 마지막 20바이트 | 80~99 (20바이트) | `bytes 80-99/100` |

  응답 예:

  ```text
  HTTP/1.1 206 Partial Content
  Content-Type: application/octet-stream
  Content-Length: 10
  Content-Range: bytes 0-9/100
  Accept-Ranges: bytes
  Connection: close

  (0~9번 바이트)
  ```

  `Content-Range`의 `/` 뒤 숫자는 파일 전체 크기다. 재생기는 이 값으로 파일 크기를 안다.
- **이 change에서:** specs "범위 요청", design 결정 7.

#### `416 Range Not Satisfiable`

- **정의:** 요청한 범위가 파일 안에 한 바이트도 없을 때의 응답.
- **동작:** 크기 100인 파일에 `bytes=100-`(100번은 파일 밖)를 요청하면 `416`과 `Content-Range: bytes */100`으로 응답한다. `*`는 "보낸 범위 없음"이고, 클라이언트는 `/` 뒤의 크기를 보고 요청을 고칠 수 있다.
- **이 change에서:** specs "만족할 수 없는 범위".

#### 범위를 무시하는 경우

- **정의:** HTTP 규격(RFC 9110)은 서버가 `Range`를 처리할 수 없거나 처리하지 않기로 하면 `Range`를 무시하고 파일 전체를 `200`으로 보내도 된다고 정한다.
- **왜 필요한가:** 범위 여러 개(`bytes=0-9,20-29`)에 응답하려면 `multipart/byteranges`라는 별도 본문 형식이 필요하다. HLS 재생기는 범위를 하나씩만 요청하므로 이 형식을 만들지 않고, 여러 범위는 무시한다. 형식이 잘못된 `Range`도 규격에 따라 무시한다.
- **이 change에서:** specs "범위 요청 무시".

#### `If-Range`

- **정의:** "파일이 내가 전에 받은 버전과 같을 때만 범위로 보내고, 바뀌었으면 전체를 보내라"는 조건 헤더. 값은 서버가 전에 보낸 `ETag`(파일 버전 식별 문자열)나 `Last-Modified`(수정 시각)다.
- **왜 필요한가:** 클라이언트가 파일 앞부분을 받아 두고 나머지를 범위로 받을 때, 그 사이 파일이 바뀌었으면 앞뒤가 맞지 않는다.
- **동작:** 이 서버는 `ETag`와 `Last-Modified`를 보내지 않으므로 같은 버전인지 판단할 수 없다. 그래서 `If-Range`가 오면 규격이 허용하는 대로 `Range`를 무시하고 전체를 보낸다.
- **이 change에서:** specs "범위 요청 무시", design 결정 7.

#### `Accept-Ranges: bytes`

- **정의:** "이 서버는 이 자원에 바이트 단위 범위 요청을 받는다"고 알리는 응답 헤더.
- **동작:** 클라이언트는 이 헤더를 보고 범위 요청을 써도 되는지 판단한다. 파일 내용을 담은 `200`과 `206` 응답에 넣는다.
- **이 change에서:** specs "응답 헤더".
